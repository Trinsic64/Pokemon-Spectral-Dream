# AI Event Editing Instructions

This document tells an AI coding agent everything it needs to operate the event editing
toolchain in `DSPRE-Contents-Analysis/`. Read this fully before executing any task.

---

## 1. Directory Layout

```
DSPRE-Contents-Analysis/
├── events/
│   ├── raw/                    # Original binary event files (DO NOT EDIT)
│   ├── edited/                 # Output binary event files (generated by serialize_events.py)
│   ├── backups/                # Timestamped snapshots (created by backup_events.py)
│   ├── overworlds.csv          # All NPC / trainer / item-ball overworlds  ← EDIT SURFACE
│   ├── warps.csv               # All warps                                 ← EDIT SURFACE
│   ├── spawnables.csv          # All floor items / hidden items             ← EDIT SURFACE
│   ├── triggers.csv            # All trigger zones                          ← EDIT SURFACE
│   ├── events-summary.csv      # Per-event-file entity counts (read-only)
│   ├── event-script-map.csv    # Entity → script file cross-reference
│   ├── map-permissions.csv     # Per-map walkable/blocked tile counts
│   └── changelog.csv           # Append-only log of all edits
├── unpacked/
│   ├── eventFiles/             # Original binary event files (DO NOT EDIT)
│   ├── maps/                   # Binary map files with collision grids
│   └── matrices/               # Binary matrix files linking map IDs
├── constants/                  # CSV lookups: species, items, moves, abilities, trainerclasses, maps
├── tools/                      # Python scripts (the toolchain)
└── INDEX.md                    # Overview of all directories
```

**Critical rule**: Never edit files in `events/raw/`, `unpacked/`, or the source ROM directory
`ROM/Pokemon-Spectral-Dream_DSPRE_contents/`. All edits go through CSVs and are serialized
to `events/edited/`.

---

## 2. The Edit Pipeline

Every event edit follows this exact sequence:

```
1. BACKUP     →  python tools/backup_events.py create --name <descriptive_name>
2. PLAN       →  Identify event file, entity type, and changes needed
3. PLACE      →  python tools/map_lookup.py --event NNNN --suggest-placement  (for new events)
4. FLAG       →  python tools/flag_registry.py allocate 1  (if the event needs a flag)
5. EDIT       →  Either:
                   a) Manual CSV edit via batch_edit.py manifest (preferred for bulk)
                   b) Direct CSV edit for single changes
6. SERIALIZE  →  python tools/serialize_events.py --event NNNN --validate
7. VERIFY     →  Check the output in events/edited/NNNN matches expected byte size
8. SCRIPT     →  python tools/script_templates.py <template> --flag N --item N --script-num N
                   (if adding new scripted events, generate the script text)
```

## 3. Tool Reference

All tools are in `DSPRE-Contents-Analysis/tools/` and use Python standard library only.
Run from the `DSPRE-Contents-Analysis/` directory.

### 3.1 backup_events.py — Version Control

```bash
python tools/backup_events.py create --name my_backup    # Create a named snapshot
python tools/backup_events.py list                        # Show all backups
python tools/backup_events.py diff my_backup              # Compare current state to backup
python tools/backup_events.py restore my_backup           # Restore from backup
```

**Always create a backup before any edit session.**

### 3.2 map_lookup.py — Map & Collision Data

```bash
# Indoor map (small matrix ≤3x3): shows full collision grid
python tools/map_lookup.py --header 11 --visual --suggest-placement

# Overworld map (large matrix): must specify matrix cell
python tools/map_lookup.py --header 10 --matrix-pos 30,38 --visual --suggest-placement

# Look up by event file number
python tools/map_lookup.py --event 0057

# List walkable coordinates
python tools/map_lookup.py --header 11 --walkable
```

Output legend:
- `.` = walkable tile
- `#` = blocked tile (wall/obstacle)
- `?` = special tile (terrain feature)
- `@` = existing event entity at this position
- `*` = suggested placement position (safe, walkable, away from walls, not occupied)

The `--suggest-placement` flag returns up to 10 positions that are:
- On walkable tiles (collision == 0x00)
- Inside the playable bounding box (filters out empty map padding in indoor maps)
- Not already occupied by an existing overworld or spawnable
- At least 2 Manhattan distance from any blocked tile

### 3.3 flag_registry.py — Flag Management

```bash
python tools/flag_registry.py status                      # Show available flag count
python tools/flag_registry.py allocate 1                  # Allocate 1 flag, returns decimal ID
python tools/flag_registry.py check 2571                  # Check if flag 2571 is available
python tools/flag_registry.py release 2571                # Release a flag back to available
```

Flags are tracked in `Data/Flag-Data/Flag-Data-Main.csv`. Any event that should only
trigger once (item pickups, one-time NPCs) requires a unique flag.

### 3.4 batch_edit.py — Bulk Edits via JSON Manifest

```bash
python tools/batch_edit.py manifest.json --dry-run        # Preview changes
python tools/batch_edit.py manifest.json --backup         # Apply with automatic backup
python tools/batch_edit.py manifest.json                  # Apply changes
```

Manifest format:
```json
{
    "description": "Add item balls to Route 5",
    "edits": [
        {
            "action": "modify_overworld",
            "event_file": "0057",
            "index": 2,
            "changes": {"overlay_entry": "522"}
        },
        {
            "action": "add_overworld",
            "event_file": "0057",
            "data": {
                "ow_id": "10", "overlay_entry": "87", "type": "ITEM",
                "movement": "0", "flag": "2571", "script": "10",
                "orientation": "1", "sight_range": "0",
                "x_range": "0", "y_range": "0",
                "x_map": "16", "x_matrix": "0",
                "y_map": "16", "y_matrix": "0", "z": "0"
            }
        },
        {
            "action": "remove_overworld",
            "event_file": "0057",
            "index": 5
        }
    ]
}
```

Supported actions: `modify_overworld`, `add_overworld`, `remove_overworld`,
`modify_warp`, `add_warp`, `remove_warp`,
`modify_spawnable`, `add_spawnable`, `remove_spawnable`,
`modify_trigger`, `add_trigger`, `remove_trigger`.

**After batch_edit, always re-serialize affected event files.**

### 3.5 serialize_events.py — CSV → Binary

```bash
python tools/serialize_events.py --event 0057 --validate  # Serialize one event file
python tools/serialize_events.py --validate                # Serialize all event files
```

Output goes to `events/edited/NNNN`. The `--validate` flag checks for:
- Duplicate `ow_id` values (warns but proceeds)
- Entity count changes vs. original raw file (warns but proceeds)

### 3.6 script_templates.py — Generate Script Text

```bash
python tools/script_templates.py list                                           # List templates
python tools/script_templates.py item-pickup --flag 2571 --item 1 --script-num 5
python tools/script_templates.py npc-dialogue --script-num 3
python tools/script_templates.py hm-rocksmash --script-num 7
python tools/script_templates.py hm-cut --script-num 8
python tools/script_templates.py trainer-battle --trainer-id 50 --script-num 2
```

Templates output DSPRE script text. The `--script-num` must match the `script` field
in the overworld CSV entry that triggers it.

### 3.7 event_script_map.py — Entity ↔ Script Cross-Reference

```bash
python tools/event_script_map.py --summary                # Regenerate cross-reference CSV
```

Writes `events/event-script-map.csv` linking 3,092 entities to their script files.

### 3.8 reclassify_trainer.py — Change Trainer Class & Sprite

```bash
python tools/reclassify_trainer.py list-classes                                  # Show all 137 classes
python tools/reclassify_trainer.py reclassify --trainer-id 1 --new-class TRAINERCLASS_HIKER --new-owid 333 --dry-run
python tools/reclassify_trainer.py reclassify --trainer-id 1 --new-class TRAINERCLASS_HIKER --new-owid 333
```

Atomically updates four files:
1. `Data/Trainer-Data/Trainer-Data-Main.csv`
2. `Data/Trainer-Data/Trainers/T{ID}-{NAME}/meta.json`
3. `Tools/hg-engine/armips/data/trainers/trainers.s`
4. `DSPRE-Contents-Analysis/events/overworlds.csv`

### 3.9 parse_events.py — Binary → CSV (Re-parse)

```bash
python tools/parse_events.py                              # Re-parse all raw event files to CSVs
```

Regenerates all event CSVs from `events/raw/`. Use after restoring a backup.

### 3.10 parse_map_permissions.py — Map Collision Summary

```bash
python tools/parse_map_permissions.py                     # Parse all maps to CSV
python tools/parse_map_permissions.py --map 0216 --visual # Show one map visually
```

### 3.11 parse_constants.py — hg-engine Constants → CSV

```bash
python tools/parse_constants.py                           # Re-export constants from hg-engine headers
```

## 4. Data Format Reference

### 4.1 Overworld CSV Columns

| Column | Type | Description |
|--------|------|-------------|
| event_file | string | Zero-padded 4-digit event file ID (e.g. "0057") |
| index | int | Entity index within this event file (0-based) |

| x_map | int | X position within the 32x32 map tile (0-31) |
| y_map | int | Y position within the 32x32 map tile (0-31) |
| x_matrix | int | X position of the matrix cell this entity is in |
| y_matrix | int | Y position of the matrix cell this entity is in |
| z | int | Z position (elevation, usually 0) |

## 5. Coordinate System

Event positions use a two-level coordinate system:

```
Global position = (x_matrix * 32 + x_map,  y_matrix * 32 + y_map)
```

- **x_map / y_map**: Position within a single 32x32 map tile (0-31)
- **x_matrix / y_matrix**: Which cell in the game matrix grid this tile belongs to

For indoor maps (matrix ≤ 3x3), x_matrix and y_matrix are typically 0.
For the overworld (matrix 0, 40x40), these identify which terrain chunk the entity is on.

## 6. How Item Balls Work (CRITICAL)

For overworlds with `type=ITEM`, the `script` field does NOT reference the map's own
script file. Instead, it references **script file 141** (the field item script file),
where each script directly maps to an item:

```
script number in event file = item_ID + 1
```

Script file 141 contains 800 scripts (Script 1 through Script 800). Each one follows
this pattern:

```
Script N:
    SetVar 0x8008 (N-1)    ← this is the item ID
    SetVar 0x8009 1         ← quantity
Jump Function#1             ← calls the pickup handler (Script 801)
```

**To place an item ball that gives a specific item:**
1. Look up the item ID in `constants/items.csv` (the `value` column)
2. Set the overworld's `script` field to `item_ID + 1`
3. Set `type` to `ITEM`, `overlay_entry` to `87` (item ball sprite)
4. Assign a unique flag so it disappears after pickup

**Examples:**
| Item | Item ID | Script Number |
|------|---------|---------------|
| ITEM_RARE_CANDY | 50 | 51 |
| ITEM_GENGARITE | 656 | 657 |
| ITEM_KEY_STONE | 773 | 774 |
| ITEM_MAX_REVIVE | 29 | 30 |

Items with ID >= 800 may not have entries in script file 141. Check the file first.

The pickup handler (Script 801 / Function#1 in file 141) automatically handles:
- Checking bag space
- Giving the item to the player
- Removing the overworld sprite
- Displaying the correct item name and pocket

**No additional map script is needed for item balls.** The event file data alone
is sufficient to define the item pickup.

## 7. Overworld Sprite Tags (overlay_entry)

The `overlay_entry` field maps to the `tag` column in
`Tools/hg-engine/src/field/overworld_table.c`. Common values:

| Tag | Species/NPC | Notes |
|-----|-------------|-------|
| 87 | ITEM_BALL | Generic item ball sprite (used for type=ITEM overworlds) |
| 317 | Youngster Joey | First trainer NPC |
| 521 | Abra | Custom overworld sprite |
| 522 | Kadabra | Custom overworld sprite |

Look up the full table in `overworld_table.c` by searching for the `gOverworldTable` array.
The array index position is the tag number. For item-ball overworlds, use tag `87`.

## 7. Common Task Workflows

### 7.1 Add an Item Ball to a Map

Item balls are self-contained in the event file -- **no map script editing needed**.
The `script` field = `item_ID + 1` (references script file 141 automatically).
See Section 6 for full details on how this works.

```bash
# 1. Backup
python tools/backup_events.py create --name before_item_add

# 2. Find the event file for the target map
#    Look up "Event File" column in Data/Header-Data/Header-Data-Main.csv

# 3. Find the item ID in constants/items.csv
#    Example: ITEM_RARE_CANDY = 50, so script = 51
#    Example: ITEM_GENGARITE = 656, so script = 657

# 4. Allocate a flag (item disappears when this flag is set after pickup)
python tools/flag_registry.py allocate 1
# Output: Allocated flag 64 (0x40)

# 5. Find a safe position
python tools/map_lookup.py --event NNNN --visual --suggest-placement

# 6. Create manifest (script = item_ID + 1)
# Save as add_item.json:
{
    "description": "Add Rare Candy item ball to map",
    "edits": [{
        "action": "add_overworld",
        "event_file": "NNNN",
        "data": {
            "ow_id": "NEXT_AVAILABLE",
            "overlay_entry": "87",
            "type": "ITEM",
            "movement": "0",
            "flag": "64",
            "script": "51",
            "orientation": "1",
            "sight_range": "0",
            "x_range": "0", "y_range": "0",
            "x_map": "FROM_SUGGESTION",
            "y_map": "FROM_SUGGESTION",
            "x_matrix": "FROM_SUGGESTION",
            "y_matrix": "FROM_SUGGESTION",
            "z": "0"
        }
    }]
}

# 7. Dry-run then apply
python tools/batch_edit.py add_item.json --dry-run
python tools/batch_edit.py add_item.json

# 8. Serialize
python tools/serialize_events.py --event NNNN --validate
```

To find the correct `ow_id`, check `overworlds.csv` for the target event file and use
a number that doesn't conflict. For type=ITEM overworlds, ow_id can be any unique value.

**No script template or map script editing is needed for item balls.** The pickup
logic is handled entirely by script file 141's pre-built handlers.

### 7.2 Change an NPC Sprite

```bash
# 1. Backup

# 2. Find the entity in overworlds.csv (event_file + index)

# 3. Create manifest

    "edits": [{
        "action": "modify_overworld",
        "event_file": "NNNN",
        "index": IDX,
        "changes": {"overlay_entry": "NEW_TAG"}
    }]
}

# 4. Apply and serialize
python tools/batch_edit.py manifest.json --backup
python tools/serialize_events.py --event NNNN --validate
```

### 7.3 Reclassify a Trainer (Class + Battle Sprite + OW Sprite)

```bash

python tools/reclassify_trainer.py list-classes

# 2. Dry-run
python tools/reclassify_trainer.py reclassify --trainer-id TID --new-class TRAINERCLASS_NAME --new-owid NEW_TAG --dry-run

# 3. Apply
python tools/reclassify_trainer.py reclassify --trainer-id TID --new-class TRAINERCLASS_NAME --new-owid NEW_TAG

# 4. Serialize all affected event files
python tools/serialize_events.py --validate
```

## 8. Constraints and Warnings

1. **ow_id uniqueness**: Each overworld entity within the same event file must have a
   unique `ow_id`. The serializer warns about duplicates. Trainers especially must have
   unique IDs to avoid battle system bugs.

2. **NPC count limits**: Too many unique NPC sprites on a single map area causes rendering
   glitches. The NDS has limited VRAM for overworld sprites. Keep the total number of
   distinct `overlay_entry` values per event file reasonable (under ~15 unique sprites).

3. **Flag exhaustion**: There are 242 available flags. Each item ball, one-time NPC, or
   one-time event needs a unique flag. Track allocations carefully.

4. **Script file linkage**: The `script` field in overworld/spawnable/trigger CSVs
   references a `Script N:` block in the map's `.script` file. The script file number
   is found via `Header-Data-Main.csv` → `Script File` column.

5. **Round-trip integrity**: The serialize pipeline preserves all unknown binary fields.
   However, if you add or remove entities, the entity count in the binary header changes.
   This is normal and handled correctly.

6. **Edited binaries go to `events/edited/`**: Copy the edited binary files into a
   duplicate ROM's `unpacked/eventFiles/` directory and repack with DSPRE for testing.
   Never overwrite the original ROM's event files directly.

7. **Overworld matrix for towns/routes**: Towns and routes use matrix 0 (the 40x40
   overworld matrix). To query collision data for these, you need to know the specific
   matrix cell [row,col] where the event entities are. Check the entity's `x_matrix`
   and `y_matrix` values in overworlds.csv, then use `--matrix-pos ROW,COL`.

## 10. Error Recovery

If something goes wrong:

```bash
# List available backups
python tools/backup_events.py list

# Compare current state to a backup
python tools/backup_events.py diff <backup_name>

# Restore from backup (overwrites current CSVs and raw binaries)
python tools/backup_events.py restore <backup_name>

# Re-parse raw binaries to CSVs (after restoring raw files)
python tools/parse_events.py
```
